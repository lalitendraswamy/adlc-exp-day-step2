**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**

- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.\*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** The implementation should center on `src/backend/OuterloopLabApi.sln` as the required .NET entrypoint, `src/backend/Program.cs` for startup/configuration/DI and Cosmos availability checks, `src/backend/Controllers/CurrencyConversionsController.cs` (or equivalent route definitions kept in `src/backend/Program.cs` if the API currently uses minimal APIs), `src/backend/Services/CurrencyApiClient.cs`, `src/backend/Services/CurrencyConversionService.cs`, `src/backend/Services/AuditTrailRepository.cs`, and request/response/domain models under `src/backend/Models/`. On the UI side, the work should center on `src/frontend/index.html` for the `__VITE_API_URL__` runtime placeholder, `src/frontend/src/main.jsx`, and `src/frontend/src/App.jsx`; assumption: if the frontend is already TypeScript-based, keep the same file roles with `.tsx` equivalents rather than changing the app structure.

**In Scope:**

- Add a backend endpoint that accepts a conversion request (`amount`, `fromCurrency`, `toCurrency`), calls the external currency provider through an internal adapter, calculates the converted amount, persists an audit record, and returns both the computed result and the audit identifier.
- Add a backend endpoint that retrieves a single stored conversion audit record by identifier and returns the original amount, currencies, rate, provider date/sequence marker, backend execution timestamp, and converted amount.
- Normalize external provider data into an internal audit model so the audit trail is stable even if the upstream JSON naming differs.
- Store each successful conversion as a Cosmos DB document that can be reconstructed later without recomputing the rate.
- Add a frontend form in `src/frontend/src/App.jsx` for entering amount/source currency/target currency and displaying the returned conversion result immediately.
- Add a frontend audit lookup interaction that lets the user paste an audit ID and view the stored conversion details returned by the backend.
- Show user-friendly validation and failure states in the UI for invalid input and provider/backend unavailability.

**Out of Scope:**

- Authentication, authorization, or tenant-specific access control.
- Bulk conversion uploads, spreadsheet import/export, or batch settlement workflows.
- Historical search/filter/reporting beyond direct lookup of a known audit record identifier.
- Scheduled rate caching, background refresh jobs, or analytics dashboards.
- Editing or deleting audit records after creation.
- Provisioning new Azure infrastructure outside the application startup behavior already required by Known Constraints.

**Feature Constraints:**

- Use `IHttpClientFactory` for the outbound currency-provider client and keep all provider-specific parsing inside a single adapter class so the rest of the application depends only on an internal normalized result model.
- Use `decimal` for monetary amount, exchange rate, and converted amount calculations; round the returned converted amount to 2 decimal places using a consistent midpoint rule and persist the rounded value that was shown to the user.
- Accept and persist only uppercase 3-letter ISO-style currency codes at the API boundary; reject malformed codes or non-positive amounts with a `400` response using `ProblemDetails`.
- Persist each audit document with, at minimum, a stable `id`, original amount, source currency, target currency, normalized rate, converted amount, provider date/sequence marker, exact backend execution timestamp in UTC, and enough provider-source metadata to identify which upstream source produced the rate.
- Map upstream transport, timeout, or parsing failures to a domain-specific error path and return a `503` `ProblemDetails` response without leaking raw exception text, stack traces, or provider-specific serialization details.
- Keep the frontend read-only with respect to audit history: it may create a new conversion and fetch an existing audit record, but it must not offer update/delete actions.

**Expected Outcome:** A user can open the React UI, enter a valid amount and currency pair, submit once, and immediately see a converted amount plus an audit ID coming from the backend. For example, if the user submits `{ "amount": 100.00, "fromCurrency": "USD", "toCurrency": "EUR" }` and the normalized provider result yields a rate of `0.92` with provider date marker `2026-08-01`, the successful backend response should include `convertedAmount: 92.00`, `rate: 0.92`, a non-empty `auditId`, and an `executedAtUtc` value formatted as a full ISO-8601 UTC timestamp with sub-second precision (for example `2026-08-01T14:23:45.123Z`). A later fetch of that `auditId` must return the same persisted values without recalculating them. If the provider call fails or times out, the create-conversion endpoint must return a `ProblemDetails` response with HTTP status `503` and a clear feature-level message such as "Currency rate provider is currently unavailable," not a raw network or JSON exception.
